# レビュー観点表

> **使用方法**: 各工程でレビューを行う際に、該当セクションの観点を使用してチェックしてください。
> プロジェクト固有の観点は、このファイルに追記するか、プロジェクト別ファイルを作成してください。

---

## 1. 要求仕様レビュー観点

### 1.1 完全性

- [ ] すべてのステークホルダーの要求が網羅されているか
- [ ] 機能要求と非機能要求の両方が記載されているか
- [ ] 各要求に「理由」が記述されているか（USDM必須要素）
- [ ] 各要求に対応する「仕様」が存在するか
- [ ] 前提条件・制約事項が明記されているか
- [ ] 用語定義が記載されているか

### 1.2 一貫性

- [ ] 要求間に矛盾がないか
- [ ] 用語が統一されているか
- [ ] トレーサビリティタグ（REQ-XXX, SPEC-XXX）が付与されているか
- [ ] タグの重複がないか

### 1.3 明確性

- [ ] 要求が曖昧でなく、一意に解釈できるか
- [ ] 「など」「適切に」「必要に応じて」等の曖昧な表現がないか
- [ ] 仕様が検証可能な形で記述されているか（数値基準、条件等）
- [ ] 各仕様に検証方法が明記されているか

### 1.4 実現可能性

- [ ] 技術的に実現可能な仕様か
- [ ] 制約条件（予算、期間、リソース）内で実現可能か
- [ ] 相反する非機能要求のトレードオフが検討されているか

### 1.5 リスク

- [ ] リスク分析が行われているか
- [ ] 各リスクに対処策が策定されているか
- [ ] 影響度と発生確率の評価が妥当か

---

## 2. 方式設計レビュー観点

### 2.1 要求充足

- [ ] すべてのSPEC-XXXが方式設計要素（ARC-XXX）に割り当てられているか
- [ ] traces-toが正しく記載されているか
- [ ] 非機能要求が設計に反映されているか

### 2.2 設計妥当性

- [ ] 設計方針・原則が明記されているか
- [ ] コンポーネント分割の粒度が適切か（高凝集・低結合）
- [ ] コンポーネント間のインターフェースが明確か
- [ ] データモデルが要求を満たしているか
- [ ] 技術選定の理由が明記されているか

### 2.3 エラー処理・安全性

- [ ] エラー処理方針が定義されているか
- [ ] セキュリティ設計が行われているか
- [ ] 障害時の復旧方針が検討されているか

### 2.4 拡張性・保守性

- [ ] 将来の機能追加を想定した設計か
- [ ] モジュール間の依存関係が最小化されているか
- [ ] 設定値が外部化されているか

---

## 3. 詳細設計レビュー観点

### 3.1 方式設計との整合性

- [ ] すべてのARC-XXXが詳細設計要素（DET-XXX）に展開されているか
- [ ] traces-toが正しく記載されているか
- [ ] 方式設計のインターフェース仕様が詳細化されているか

### 3.2 設計品質

- [ ] クラス・関数の責務が単一か（単一責任原則）
- [ ] パラメータの型・制約が明記されているか
- [ ] 戻り値の型・条件が明記されているか
- [ ] 例外処理が漏れなく定義されているか
- [ ] エラーコードが体系的に定義されているか

### 3.3 データ設計

- [ ] データベーステーブル定義が正規化されているか
- [ ] インデックス設計が行われているか
- [ ] NULL許可の判断が適切か
- [ ] データ量見積もりが行われているか

### 3.4 処理フロー

- [ ] アルゴリズムが記述されているか
- [ ] 処理の前提条件・事後条件が明記されているか
- [ ] 状態遷移が存在する場合、遷移図が記述されているか
- [ ] 並行処理時の排他制御が考慮されているか

---

## 4. テスト設計レビュー観点

### 4.1 テストカバレッジ

- [ ] テスト対象の全機能に対するテストケースが存在するか
- [ ] 正常系・異常系・境界値のテストケースが網羅されているか
- [ ] traces-toで設計要素との対応が明記されているか

### 4.2 テストケース品質

- [ ] テスト手順が具体的で再現可能か
- [ ] 期待結果が明確に記述されているか
- [ ] テストデータが準備されているか
- [ ] 前提条件が明記されているか

### 4.3 テスト環境

- [ ] テスト環境の構成が明記されているか
- [ ] テスト完了基準が定義されているか
- [ ] テスト結果の記録方法が決まっているか

### 4.4 境界値テスト

- [ ] 数値の上限・下限のテストが含まれているか
- [ ] 文字列の最大長・空文字のテストが含まれているか
- [ ] コレクションの空・1件・最大件数のテストが含まれているか

---

## 5. ソースコードレビュー観点

### 5.1 トレーサビリティ

- [ ] Docstring/コメントに `@trace DET-XXX` タグが記載されているか
- [ ] テストコードに `@trace UT-XXX` / `IT-XXX` / `QT-XXX` タグが記載されているか

### 5.2 コード品質

- [ ] 命名規則が一貫しているか
- [ ] 関数の行数が適切か（目安: 50行以内）
- [ ] ネストの深さが適切か（目安: 3段以内）
- [ ] マジックナンバーが定数化されているか
- [ ] コメントが必要な箇所に記述されているか

### 5.3 エラー処理

- [ ] 入力バリデーションが行われているか
- [ ] 例外が適切にハンドリングされているか
- [ ] エラーメッセージが分かりやすいか
- [ ] リソース（ファイル、DB接続等）が確実に解放されているか

### 5.4 セキュリティ

- [ ] SQLインジェクション対策がされているか
- [ ] XSS対策がされているか
- [ ] 秘密情報がハードコードされていないか
- [ ] ログに機密情報が含まれていないか

---

## 6. 対話ログ レビュー観点

### 6.1 記録の完全性

- [ ] メタデータ（日時、参加者、工程、関連成果物）が記入されているか
- [ ] 対話の目的が明記されているか
- [ ] 人間の発言が正確に記録されているか（要約しすぎていないか）
- [ ] エージェントの応答・推論プロセスが記録されているか
- [ ] タイムスタンプが付与されているか

### 6.2 決定事項の記録

- [ ] 重要な決定が「決定事項」セクションに明記されているか
- [ ] 決定の理由が記録されているか
- [ ] 影響範囲が特定されているか
- [ ] traces-to タグが付与されているか

### 6.3 アクション管理

- [ ] 未解決事項が「未解決事項」セクションに記録されているか
- [ ] 生成・更新された成果物が記録されているか
- [ ] 対話索引（conversation-index.md）が更新されているか

### 6.4 知見の蓄積

- [ ] 対話から得られた知見が記録されているか
- [ ] `knowledge/trouble-cases.md` に追記すべき内容が反映されているか

---

## 7. 成果物間 整合性レビュー観点

### 7.1 用語の統一性

- [ ] 同じ概念に対して異なる用語が使われていないか
- [ ] 略語の定義が統一されているか

### 7.2 数値・定量基準の一貫性

- [ ] パフォーマンス目標値が文書間で一致しているか
- [ ] 容量・サイズの制限値が一致しているか

### 7.3 機能範囲の整合性

- [ ] 上流文書の機能がすべて下流文書に含まれているか
- [ ] スコープクリープ（範囲外の追加）がないか

### 7.4 非機能要求の反映

- [ ] セキュリティ・性能・可用性の要件が設計に反映されているか

### 7.5 トレーサビリティの完全性

- [ ] すべてのタグがチェーンで繋がっているか（REQ→SPEC→ARC→DET→UT→IT→QT）
- [ ] 欠落しているトレースがないか

---

## 8. メトリクス品質ゲート レビュー観点

### 8.1 メトリクス計測の妥当性

- [ ] 計測対象が正しく選定されているか
- [ ] 計測方法が再現可能か
- [ ] 閾値の根拠が妥当か（`knowledge/quality-metrics.md` 参照）

### 8.2 品質ゲート判定

- [ ] 必須ゲートがすべて通過しているか
- [ ] 推奨ゲートの未達項目に合理的な理由があるか
- [ ] メトリクスログが `metrics-log.md` に記録されているか

---

## 9. 形式的仕様 レビュー観点

### 9.1 契約記述

- [ ] Public関数に前提条件・事後条件が記述されているか
- [ ] クラスに不変条件が記述されているか
- [ ] 前提条件と事後条件が論理的に矛盾していないか

### 9.2 状態遷移

- [ ] 状態遷移表がMermaid状態遷移図と一致しているか
- [ ] すべての状態×イベントの組み合わせが定義されているか（未定義遷移がないか）
- [ ] ガード条件が排他的かつ網羅的か

### 9.3 スキーマ定義

- [ ] APIにスキーマ定義（OpenAPI/JSON Schema等）があるか
- [ ] スキーマが成果物のテキスト記述と一致しているか

---

## 10. FMEA/FTA レビュー観点

### 10.1 FMEA

- [ ] 全コンポーネントの故障モードが洗い出されているか
- [ ] 深刻度(S)・発生頻度(O)・検出可能性(D)の評価が妥当か
- [ ] RPN ≥ 100 の項目に対策が記載されているか
- [ ] 対策後のRPNが再評価されているか

### 10.2 FTA

- [ ] RPN ≥ 100 のトップ事象に対してFTAが実施されているか
- [ ] 根本原因が十分に深掘りされているか
- [ ] 各根本原因に対策が定義されているか
- [ ] 対策のテストケースが特定されているか

---

## 11. レビュープロトコル レビュー観点

### 11.1 ウォークスルー

- [ ] 著者が成果物の全体構造を説明しているか
- [ ] 設計判断のポイントと理由が説明されているか
- [ ] リスクと懸念が明示されているか
- [ ] 指摘事項にRV-XXXタグが付与されているか

### 11.2 インスペクション

- [ ] 指摘に深刻度（Critical/Major/Minor/Info）が付与されているか
- [ ] 指摘に分類コード（REQ-MISS/DES-ERR等）が付与されているか
- [ ] Critical/Major指摘がすべて修正されているか
- [ ] 修正の確認がモデレータによって行われているか
