## 5. レビュー・品質チェック手順

### 成果物レビュー時の手順

1. 対象成果物のトレーサビリティタグの整合性を確認する
2. `knowledge/review-perspectives.md` の該当工程の観点表を参照する
3. `knowledge/trouble-cases.md` の関連事例を確認する
4. `knowledge/checklists.md` の該当工程チェックリストを使用する
5. 指摘事項にはレビュー指摘タグ `RV-XXX` を付与する

### レビュー指摘の重要度

| レベル | 意味 | 対応 |
|--------|------|------|
| **Critical** | 要求未充足・安全性問題 | 必ず修正 |
| **Major** | 設計不備・性能問題 | 修正推奨 |
| **Minor** | 記述改善・可読性 | 検討 |
| **Info** | 参考情報・提案 | 任意 |

## 21. メトリクス駆動 品質ゲート

### 目的

各工程の品質を**定量的に計測**し、閾値を満たさない場合は工程完了を認めない。「チェックリストを通ったか」ではなく「数値で品質を証明する」。

### 工程別メトリクス定義

| 工程 | メトリクス | 計測方法 | 閾値 | ゲート |
|------|----------|---------|------|--------|
| SWP.1 要求仕様 | 要求あたり仕様数 | SPEC数 ÷ REQ数 | ≥ 2.0 | 必須 |
| SWP.1 要求仕様 | 曖昧語出現率 | 曖昧語数 ÷ 総文数 × 100 | 0% | 必須 |
| SWP.1 要求仕様 | 要求カバレッジ | 仕様付き要求数 ÷ 全要求数 × 100 | 100% | 必須 |
| SWP.2 方式設計 | コンポーネント結合度 | 依存先コンポーネント数の平均 | ≤ 3 | 必須 |
| SWP.2 方式設計 | インターフェース定義率 | 定義済みIF数 ÷ 全IF数 × 100 | 100% | 必須 |
| SWP.3 詳細設計 | 関数あたり予測複雑度 | McCabe予測値の平均 | ≤ 10 | 推奨 |
| SWP.3 詳細設計 | 契約記述率 | 前提/事後条件付き関数数 ÷ 全関数数 | ≥ 80% | 推奨 |
| SWP.4 単体テスト | C1カバレッジ | 分岐カバレッジ％ | ≥ 80% | 必須 |
| SWP.4 単体テスト | テスト密度 | テストケース数 ÷ KLOC | ≥ 50 | 推奨 |
| SWP.4 実装 | コード重複率 | 重複行数 ÷ 総行数 × 100 | ≤ 5% | 必須 |
| SWP.4 実装 | 技術的負債比率 | 負債工数 ÷ 開発工数 × 100 | ≤ 5% | 推奨 |
| SWP.5 結合テスト | インターフェースカバレッジ | テスト済みIF数 ÷ 全IF数 × 100 | 100% | 必須 |
| SWP.6 適格性確認 | 要求カバレッジ | テスト済みREQ数 ÷ 全REQ数 × 100 | 100% | 必須 |
| 全工程 | 欠陥密度 | 検出欠陥数 ÷ KLOC | 参考値 | 記録 |
| 全工程 | 欠陥除去率（DRE） | 検出欠陥数 ÷ (検出 + 流出) × 100 | ≥ 95% | 目標 |

### 曖昧語リスト（自動検出対象）

以下の語句が要求仕様書に含まれている場合、曖昧語として検出する:

```
等、など、適切に、必要に応じて、適宜、可能な限り、
できるだけ、通常は、基本的に、原則として、
十分な、高速な、大量の、少量の、ほぼ、約、程度、
etc., appropriate, adequate, as needed, if necessary,
sufficient, fast, large, small, approximately
```

### 品質ゲート判定フロー

```
工程完了申告
    ↓
メトリクス自動計測
    ↓
┌─ 必須ゲート全通過?
│   ├─ Yes → 推奨ゲートの結果を記録して工程完了
│   └─ No  → 未達メトリクスを報告 → 改善後に再計測
└────────────────────────────────────
```

### メトリクス記録場所

各プロジェクトのコンテキストディレクトリに `metrics-log.md` を作成し、工程完了時のメトリクス値を記録する:

```markdown
# メトリクスログ

| 計測日 | 工程 | メトリクス | 値 | 閾値 | 判定 |
|--------|------|----------|-----|------|------|
| 2025-02-14 | SWP.1 | 要求あたり仕様数 | 2.5 | ≥2.0 | ✅ |
| 2025-02-14 | SWP.1 | 曖昧語出現率 | 0% | 0% | ✅ |
```

詳細な定義と閾値の根拠は `knowledge/quality-metrics.md` を参照。

## 25. エージェント自己評価メカニズム

### 目的

エージェントが生成した成果物の品質を**エージェント自身が評価**し、品質問題を人間に提出する前に検出する。

### 自己評価のタイミング

```
成果物生成
    ↓
自己評価チェック実行
    ↓
┌─ 全項目通過?
│   ├─ Yes → 品質レポートを添付して人間に提出
│   └─ No  → 問題箇所を修正 → 再チェック（最大3回）
│            └─ 3回でも未達 → 🟡 未達項目を明示して人間に相談
└────────────────────────────────────
```

### 工程別 自己評価チェック項目

#### SWP.1 要求仕様

- [ ] 曖昧語（Section 21 リスト）がゼロか
- [ ] すべての要求に「要求」「理由」「仕様」が記述されているか
- [ ] すべての要求・仕様にトレーサビリティタグ（REQ/SPEC）が付与されているか
- [ ] 要求あたり仕様数が閾値（≥2.0）を満たすか
- [ ] 記述内容が一意に解釈できるか（主語・述語・目的語が明確か）

#### SWP.2 方式設計

- [ ] Mermaid図（コンポーネント、シーケンス、ER）がテキスト本文と一致しているか
- [ ] すべてのSPEC-XXXがARC-XXXに割り当てられているか（カバレッジ100%）
- [ ] コンポーネント結合度が閾値（≤3）を満たすか
- [ ] FMEAテーブルが作成されているか（Section 24 該当時）
- [ ] 設計制約（ADR）が明記されているか（Section 22）

#### SWP.3 詳細設計

- [ ] 前提条件・事後条件・不変条件が記述されているか（Section 23）
- [ ] 状態遷移表が作成されているか（有状態な機能の場合）
- [ ] Mermaidクラス図がテキスト本文と一致しているか
- [ ] すべてのARC-XXXがDET-XXXに展開されているか

#### SWP.4 単体テスト

- [ ] テストコードが前提条件・事後条件・境界値をカバーしているか
- [ ] テストダブル（Mock/Stub）が適切に使用されているか
- [ ] `@trace UT-XXX` タグが付与されているか
- [ ] C1カバレッジ目標に対する見通しが立っているか

#### 全成果物共通

- [ ] 文書内で用語が統一されているか
- [ ] トレーサビリティタグの体系（REQ→SPEC→ARC→DET→UT）が連鎖しているか
- [ ] 前工程の成果物との整合性が取れているか

### 自己評価レポート

成果物提出時に以下の形式で自己評価結果を添付する:

```
📊 自己評価レポート
━━━━━━━━━━━━━━━━━━━━━
✅ 通過: 8/10 項目
⚠️ 要確認: 1 項目（コンポーネント結合度 3.2 → 閾値3に微超過）
❌ 未達: 1 項目（FMEA未作成 → 安全性要求なしのため省略可能か確認）
━━━━━━━━━━━━━━━━━━━━━
```

詳細な自己評価基準は `knowledge/self-evaluation.md` を参照。

## 26. レビュープロトコル

### 目的

レビューを**場当たり的なチェック**から**体系的なプロトコル**に昇格させ、レビューの効果を最大化する。

### レビュー技法の選択基準

| 技法 | 適用場面 | 参加者 | 所要時間 | 欠陥検出力 |
|------|---------|--------|---------|----------|
| **チェックリストレビュー** | 全成果物（最低限） | 1人（エージェント） | 短 | 中 |
| **ウォークスルー** | 設計書、複雑な仕様 | 著者 + レビュワー | 中 | 中〜高 |
| **インスペクション** | 高リスク成果物 | モデレータ + レビュワー + 著者 | 長 | 高 |
| **ペアレビュー** | コード、テスト設計 | 2人（人間 + エージェント） | 中 | 中〜高 |

### ウォークスルー手順

```
1. 【準備】著者（エージェント）がレビュー資料を事前共有
2. 【説明】著者が成果物を順に説明する
3. 【質疑】レビュワー（人間）が疑問点・懸念を質問する
4. 【記録】指摘事項を記録する（RV-XXXタグ付与）
5. 【判定】修正の要否を判定する
```

ウォークスルー時のエージェントの説明テンプレート:

```markdown
## ウォークスルー: [成果物名]

### 1. 概要
この成果物は[目的]のために作成しました。[全体の構造]を説明します。

### 2. 設計判断のポイント
- [判断1]: [理由]
- [判断2]: [理由]

### 3. リスクと懸念
- [懸念点1]: [対策の考え方]
- [懸念点2]: [未解決/要検討]

### 4. 前工程との整合性
- [確認ポイント1]: ✅ 整合
- [確認ポイント2]: ⚠️ 差異あり（理由: ...）
```

### インスペクション手順

```
1. 【計画】モデレータがインスペクション範囲・観点・役割を決定
2. 【事前準備】レビュワーが個別にレビューし、指摘リストを作成
3. 【会議】指摘の統合・議論（解決策の議論は行わない ← 重要）
4. 【記録】全指摘に分類と深刻度を付与
5. 【修正】著者が修正
6. 【確認】モデレータが修正を確認
```

### 指摘の分類と深刻度

| 深刻度 | 記号 | 説明 | 対応 |
|--------|------|------|------|
| **Critical** | 🔴 | 機能に重大な影響、セキュリティ脆弱性 | 必ず修正 |
| **Major** | 🟠 | 機能に影響する可能性がある | 修正推奨 |
| **Minor** | 🟡 | 品質向上のための提案 | 検討 |
| **Info** | 🔵 | 情報共有、質問 | 記録のみ |

指摘の分類:

| 分類コード | 意味 |
|----------|------|
| `REQ-MISS` | 要求漏れ |
| `SPEC-AMB` | 仕様の曖昧性 |
| `DES-ERR` | 設計誤り |
| `DES-INC` | 設計の不完全性 |
| `COD-BUG` | コードバグ |
| `COD-STD` | コーディング規約違反 |
| `SEC-VUL` | セキュリティ脆弱性 |
| `TRC-GAP` | トレーサビリティの欠落 |
| `DOC-ERR` | 文書の誤り |
