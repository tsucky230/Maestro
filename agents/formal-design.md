## 22. アーキテクチャ適合度テスト

### 目的

方式設計で定義した**設計制約が実装で守られているか**を自動テストで継続検証する。設計書とコードの整合性を「生きたトレーサビリティ」として維持する。

### 適合度テストの種類

| カテゴリ | テスト内容 | ツール例 |
|---------|----------|---------|
| **依存関係制約** | レイヤー間の依存方向が正しいか | ArchUnit, deptry, import-linter |
| **循環依存検出** | モジュール間の循環依存がないか | madge, pydeps, jdepend |
| **パフォーマンス制約** | API応答時間が設計値以内か | k6, locust, artillery |
| **データ整合性** | DB制約が設計通りか | スキーマ比較ツール |
| **セキュリティ制約** | 認証・認可が設計通り適用されているか | OWASP ZAP, セキュリティテスト |

### 適合度テストの記述方式

方式設計書に**設計制約**を明記し、それをテストとして実装する:

```markdown
## 設計制約（Architecture Decision Records）

### ADR-001: レイヤー依存方向
- 制約: UIレイヤー → Serviceレイヤー → Repositoryレイヤー の一方向のみ
- 検証方法: 依存関係テスト（自動）
- traces-to: ARC-001

### ADR-002: API応答時間
- 制約: 全APIエンドポイントの95パーセンタイル応答時間 ≤ 200ms
- 検証方法: パフォーマンステスト（CI/CD）
- traces-to: SPEC-NF-001
```

### テストコードの例

```python
# @trace ARC-001 — レイヤー依存方向テスト
def test_ui_layer_does_not_depend_on_repository():
    """UIレイヤーがRepositoryレイヤーに直接依存していないことを検証"""
    ui_imports = analyze_imports("src/ui/")
    assert not any(imp.startswith("src.repository") for imp in ui_imports)
```

### CI/CD統合

- 適合度テストは通常のテストスイートに含め、CI/CDで自動実行する
- 設計変更時は適合度テストも同時に更新する（ADRとテストの一対一対応）
- テストに `@trace ARC-XXX` タグを付与し、設計制約とのトレーサビリティを維持する

## 23. 形式的仕様記述（軽量版）

### 目的

自然言語の仕様に**半形式的な記述**を追加することで、仕様の曖昧性を排除し、テストケースの自動導出を可能にする。

### Design by Contract（契約による設計）

すべてのPublic関数・メソッドに以下の3要素を記述する:

| 要素 | 説明 | 例 |
|------|------|-----|
| **前提条件（precondition）** | 関数が呼ばれる時に満たされているべき条件 | `age >= 0 かつ age <= 150` |
| **事後条件（postcondition）** | 関数が正常終了した時に保証される条件 | `戻り値は空でないリスト` |
| **不変条件（invariant）** | クラスの生存期間中、常に成立する条件 | `balance >= 0`（口座残高） |

### 詳細設計での記述フォーマット

```markdown
### メソッド: calculate_tax(income: int) -> int

**意図**: 所得に対する税額を計算する

**前提条件**:
- `income >= 0`
- `income` は整数値

**事後条件**:
- `戻り値 >= 0`
- `戻り値 <= income`（税額が所得を超えない）

**不変条件**:（クラスレベル）
- `self.tax_rate >= 0 かつ self.tax_rate <= 1.0`

**例外**:
- `income < 0` → `ValueError("所得は0以上である必要があります")`

**traces-to**: DET-005
```

### 状態遷移表（必須化）

Mermaid状態遷移図に加え、**状態遷移表**を必ず作成する:

| 現在状態 | イベント | ガード条件 | アクション | 次の状態 |
|---------|--------|----------|---------|---------|
| 未認証 | ログイン試行 | 認証成功 | セッション生成 | 認証済み |
| 未認証 | ログイン試行 | 認証失敗（3回未満） | エラー表示 | 未認証 |
| 未認証 | ログイン試行 | 認証失敗（3回目） | アカウントロック | ロック |
| 認証済み | ログアウト | — | セッション破棄 | 未認証 |
| ロック | 30分経過 | — | ロック解除 | 未認証 |

### API スキーマ定義

外部・内部APIには**スキーマ定義**を要求する:

- REST API → OpenAPI 3.x 仕様
- GraphQL → SDL定義
- メッセージング → JSON Schema / Avro
- データベース → DDL + 制約リスト

### テストケース自動導出

形式的仕様からテストケースを導出する手順:

1. **前提条件の境界値** → 境界値テスト（income = -1, 0, 1, MAX_INT）
2. **事後条件の検証** → 正常系テスト（結果が事後条件を満たすか）
3. **不変条件の維持** → 不変条件を破る操作がないか
4. **状態遷移表の全パス** → 状態遷移テスト（全遷移のカバー）
5. **例外条件** → 異常系テスト（明示された例外がすべて発生するか）

## 24. FMEA / FTA 統合

### 目的

システムの**潜在的な故障モード**を方式設計段階で体系的に分析し、予防策を設計に組み込む。

### FMEA（故障モード影響解析）

方式設計時に、各コンポーネントに対してFMEAテーブルを作成する:

| コンポーネント | 故障モード | 影響 | 深刻度(S) | 発生頻度(O) | 検出可能性(D) | RPN | 推奨対策 | traces-to |
|-------------|----------|------|----------|------------|-------------|-----|---------|-----------|
| 認証サービス | トークン漏洩 | 不正アクセス | 10 | 3 | 5 | 150 | トークン暗号化+有効期限短縮 | ARC-001 |
| DBコネクタ | 接続プール枯渇 | サービス停止 | 9 | 4 | 3 | 108 | コネクション数監視+自動スケール | ARC-003 |
| ファイルアップロード | サイズ超過 | メモリ不足 | 7 | 5 | 2 | 70 | ストリーミング処理+上限チェック | ARC-005 |

**評価尺度** (各1-10):

| 尺度 | 深刻度(S) | 発生頻度(O) | 検出可能性(D) |
|------|----------|------------|-------------|
| 1-3 | 軽微 | まれ | ほぼ確実に検出 |
| 4-6 | 中程度 | 時々 | 検出可能 |
| 7-10 | 重大〜壊滅的 | 頻繁 | 検出困難 |

**RPN（リスク優先度数）** = S × O × D

| RPNレンジ | リスクレベル | 対応 |
|----------|-----------|------|
| ≥ 100 | 高 | **必ず対策を実施**（設計変更または検出手段の追加） |
| 50-99 | 中 | 対策を検討し、コスト対効果を評価 |
| < 50 | 低 | 記録として残すが、対策は任意 |

### FTA（故障の木解析）

重大な障害（RPN ≥ 100）に対して、根本原因を木構造で分析する:

```
サービス停止（トップ事象）
├── [OR] ネットワーク障害
│   ├── [AND] プライマリ回線断
│   │   └── [基本事象] ISP障害
│   └── [AND] セカンダリ回線断
│       └── [基本事象] ISP障害
├── [OR] アプリケーション障害
│   ├── [基本事象] メモリリーク
│   ├── [基本事象] デッドロック
│   └── [基本事象] 未処理例外
└── [OR] インフラ障害
    ├── [基本事象] ディスク容量不足
    └── [基本事象] CPU過負荷
```

### 適用タイミング

- **方式設計（SWP.2）**: 全コンポーネントに対してFMEAを実施
- **詳細設計（SWP.3）**: RPN ≥ 100 の項目に対してFTAを実施
- **テスト設計（SWP.4-6）**: FMEA/FTAの結果をテストケースのインプットにする

テンプレートは `docs/templates/fmea-fta.md` を使用する。

### 組み込みシステム特有の故障モードテンプレート

組み込みプロジェクトでは、以下の故障モードを**必ずFMEA候補に含める**:

| コンポーネント | 故障モード | 影響 | 対策例 |
|-------------|----------|------|--------|
| WDTクリアタスク | タスクデッドロックによりWDTクリア不能 | システムリセット（意図しない再起動） | 監視タスク方式＋全タスク生存フラグ確認 |
| EEPROM/DataFlash | 書き換え寿命超過 | データ保持不能 | ウェアレベリング＋書き込み頻度監視 |
| CPUコア | CPU使用率100%到達 | デッドライン超過→制御喪失 | 過負荷検出＋優先度ベースの処理カット |
| 通信バス(SPI/I2C/CAN) | バス短絡・断線 | 通信断→状態不一致 | タイムアウト検出＋フェイルセーフ出力 |
| 電源/バッテリー | 電圧低下(LVD) | データ消失・誤動作 | LVD割込み＋不揮発データ退避シーケンス |
| 発振器/クロック | クロック異常 | タイミング精度劣化 | クロック監視回路(CSC)＋フェイルセーフクロック切替 |

### 組み込みFTAツリー例（複数CPU起動デッドロック）

```
CPU間起動デッドロック（トップ事象）
├── [AND] メインCPUがサブCPUのReady待ち
│   └── [基本事象] サブCPU初期化遅延
├── [AND] サブCPUがメインCPUの設定待ち
│   └── [基本事象] メインCPUの初期化チェック品が未送信
└── [OR] タイムアウト未設定
    ├── [基本事象] 起動シーケンスにタイムアウトなし
    └── [基本事象] タイムアウト値がHW初期化時間より短い
```

対策: `knowledge/embedded-constraints.md` §4「複数CPU通信チェックリスト」を参照。
