# トラブル事例集

> **使用方法**: 過去に発生したバグ・障害・設計ミスを構造化して登録してください。
> エージェントは設計・レビュー時にこのファイルを参照し、類似のトラブルを予防します。

---

## 登録フォーマット

各事例は以下の形式で登録してください:

```markdown
### TRB-XXX: （事例タイトル）

| 項目 | 内容 |
|------|------|
| 事例ID | TRB-XXX |
| カテゴリ | 要求不備 / 設計不備 / 実装バグ / テスト不足 / 運用問題 |
| 影響度 | Critical / Major / Minor |
| 発生工程 | SWP.1〜SWP.6 のいずれか |
| 検出工程 | （実際に発見された工程） |

**事象**: （何が起きたかを記述）

**原因**: （なぜ起きたかを記述）

**対処策**: （どう対処したかを記述）

**再発防止策**: （再発を防ぐためにどうすべきかを記述）

**チェック観点**: （レビュー時にどの観点でチェックすれば防げるかを記述）
```

## カテゴリ別事例

### 要求不備

#### TRB-001: 曖昧な要求による仕様誤解

| 項目 | 内容 |
|------|------|
| 事例ID | TRB-001 |
| カテゴリ | 要求不備 |
| 影響度 | Major |
| 発生工程 | SWP.1 (要求仕様定義) |
| 検出工程 | SWP.5 (結合テスト) |

**事象**: 「データを適切に処理する」という要求に対し、開発チームとユーザーで「適切」の解釈が異なり、結合テストで期待と異なる動作が発覚。

**原因**: 要求に「理由」と具体的な条件が記述されていなかった。

**対処策**: 要求仕様書を修正し、具体的な処理条件と数値基準を追加。

**再発防止策**: USDM形式で「理由」を必須項目とし、仕様は検証可能な形（数値・条件付き）で記述する。

**チェック観点**: 「など」「適切に」「必要に応じて」等の曖昧表現がないかチェックする。

### 設計不備

#### TRB-002: コンポーネント間インターフェース不整合

| 項目 | 内容 |
|------|------|
| 事例ID | TRB-002 |
| カテゴリ | 設計不備 |
| 影響度 | Critical |
| 発生工程 | SWP.2 (方式設計) |
| 検出工程 | SWP.5 (結合テスト) |

**事象**: コンポーネントAがJSON形式でデータを送信する想定だったが、コンポーネントBはForm形式を期待しており、結合テストでデータ連携が失敗。

**原因**: 方式設計書にインターフェースのデータ形式が明記されていなかった。

**対処策**: インターフェース仕様を方式設計書に追記し、両コンポーネントの実装を修正。

**再発防止策**: 方式設計書のインターフェース定義に、データ形式・プロトコル・エンコーディングを必ず明記する。

**チェック観点**: インターフェース定義にデータ形式が明記されているかチェックする。

### 実装バグ

#### TRB-003: 境界値処理の考慮漏れ

| 項目 | 内容 |
|------|------|
| 事例ID | TRB-003 |
| カテゴリ | 実装バグ |
| 影響度 | Major |
| 発生工程 | SWP.3 (詳細設計・製造) |
| 検出工程 | SWP.6 (適格性確認テスト) |

**事象**: ページネーション機能で、データが0件のとき「0/0ページ」と表示されエラーが発生。1件のときも「ページ1/0」と表示される不具合。

**原因**: 詳細設計で境界値（0件、1件）のケースが考慮されていなかった。

**対処策**: 0件・1件の場合の表示仕様を追加し、実装を修正。

**再発防止策**: テスト設計時に境界値テストケース（0件、1件、最大件数）を必ず含める。

**チェック観点**: 数値パラメータの0、1、最大値のケースが実装・テストに含まれているかチェックする。

---

### テスト不足

#### TRB-004: 異常系テストケース不足

| 項目 | 内容 |
|------|------|
| 事例ID | TRB-004 |
| カテゴリ | テスト不足 |
| 影響度 | Critical |
| 発生工程 | SWP.4 (単体テスト) |
| 検出工程 | 本番運用 |

**事象**: ネットワークタイムアウト時にリトライ処理が無限ループに陥り、サーバーリソースを枯渇させた。

**原因**: 正常系のテストのみ実施し、タイムアウト時の動作テストが未実施だった。

**対処策**: リトライ上限を設定し、タイムアウトテストケースを追加。

**再発防止策**: テスト設計時に「外部依存がタイムアウトした場合」「外部依存が異常応答した場合」を異常系テストケースとして必ず含める。

**チェック観点**: 外部依存（ネットワーク、DB、ファイルI/O）の異常系がテストされているかチェックする。
